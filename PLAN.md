# Repository plan

Companion repository for "Agents Are Not Microservices: Operating Autonomous AI on
Kubernetes", Cloud Native AI + Inference Day, KubeCon NA 2026, Monday 9 November 2026.

Everything here is a decision.
This file is the source of truth for the repository. Changes to it are pull requests.

## The rule

The accepted proposal is the north star. Every claim the talk makes follows one path.
Write the theory down from the proposal's own words. Test it with code we own. Say only
what the test showed.

Each pillar opens with a Kubernetes assumption, shows where it breaks for agents, and
gives a pattern.

Observability covers OpenTelemetry traces and the GenAI semantic conventions, which
are OpenTelemetry's agreed attribute names for AI systems. It is not named in the
proposal. It stays because a trace is the only way to see the other four pillars fail in
production.

## Repository

`github.com/henriquesantanati/agents-are-not-microservices`. Apache-2.0. Private while
built, public before the talk. All commits use personal identities, never an employer
identity.

## What the reader needs

A laptop with Docker or Podman, `kind`, `kubectl`, `helm` and Python 3.12. Helm is there
because the scaling lab installs KEDA and metrics-server from their charts. No GPU, no
model, no cloud account, no cost. Every lab runs on CPU with a stub agent we wrote. The
talk is about agents, not about serving models, so nothing here serves one.

## The stub agent

One Python file per lab, standard library only, no framework. It exists so the reader
sees exactly what the slide shows and nothing else.

Capabilities by pillar. Probes, hold a task and answer `/health` and `/ready`, in two
server modes, async and blocking. Scaling, one task fans out into many calls to a
fixed-capacity fake dependency, and both publish their own metrics. Disruption, run a 90 step
chain, checkpoint when asked over HTTP, on SIGTERM, or after every step, and resume
from the checkpoint.
Communication, JSON-RPC server in stateless, local-handle and A2A task modes, and a client
that either keeps one connection open or opens one per request.
Observability, emit OpenTelemetry spans and an evaluation event, delegate one step to a
stub specialist over A2A, and end and flush the open span on SIGTERM.

## Labs

Five labs, one per pillar, all the same shape.

```
labs/lib/common.sh   cluster, image loading, waiting, assertions, artifact capture
labs/kind-config.yaml the cluster config, including the hostPath the observability lab reads
labs/<pillar>/
  README.md          the theory, the commands, what to look for
  lib.sh             the lab's own helpers, and the broken and fixed observations
  00-setup.sh        checks prerequisites, creates cluster or namespace
  10-break.sh        applies the broken manifest, prints the symptom
  20-observe.sh      the kubectl commands that show why
  30-fix.sh          applies the fixed manifest
  40-verify.sh       asserts both states, exits non-zero if either fails
  99-teardown.sh
  agent/             the stub and its Dockerfile
  manifests/broken.yaml
  manifests/fixed.yaml
  artifacts/         captures used on the slides
```

The six numbered scripts stay thin. The observations and the assertions live in `lib.sh`,
so `10-break.sh` and `40-verify.sh` cannot drift apart, and the shared parts live in
`labs/lib/common.sh`.

Scripts are idempotent and exit non-zero on failure. CI runs the same files a human
does.

One `kind` cluster named `anm` serves every lab. Each lab uses its own namespace named
after the pillar and deletes only that namespace on teardown. `00-setup.sh` creates the
cluster if it is missing and never deletes it.

`artifacts/` holds plain text only, one file per capture, written by `10-break.sh` and
`30-fix.sh`. Each file is the exact terminal output of one command with a first line
naming the command and the date. No screenshots, because a screenshot cannot be diffed
or regenerated by CI.

### Probes

Theory. An agent mid-task looks fine to a probe that only checks the process is up.

Lab. Two stub deployments, async and blocking, both probing `/health`. Break shows the
async pod Ready mid-task and the blocking pod restarting. Fix moves readiness to
`/ready` and shows the async pod leave the Service endpoints while busy. The README
says plainly that the blocking server also needs to be able to answer while it works.

CI asserts the async pod's Ready condition and EndpointSlice membership in both states
and the blocking pod's restart count. No wall clock assertions.

### Scaling

Theory. One incoming task turns into many downstream calls, and the agent decides how
many at run time. So the tier that saturates is never the tier the autoscaler watches.

Lab. Stub agent plus a fake dependency, both as Deployments. Fixed values. The
dependency serves 4 calls at once and takes 200 ms per call, so one replica handles 20
calls per second. Each task makes 20 downstream calls. Load is 2 tasks per second, so
40 calls per second, twice what one dependency replica can serve.

Both stubs expose `/metrics` as JSON. The agent publishes
`agent_downstream_calls_inflight` and the dependency publishes `dependency_queue_depth`.
Nothing scrapes them. The lab scripts `curl` them, KEDA reads one of them, and CI reads
the same numbers.

Break has two observations. First, a HorizontalPodAutoscaler on the agent at 70 percent
CPU. The dependency queue grows and the HPA never fires, because the agent's CPU stays
near idle while it waits. Second, the agent is scaled by hand to three replicas and the
dependency queue does not move, because the load is set by the incoming rate times the
fan-out and more agents only spread it.

Fix returns the agent to one replica and puts a KEDA ScaledObject on the dependency,
`metrics-api` trigger, reading `dependency_queue_depth` from the dependency's own
`/metrics` through its Service, `targetValue` 10, `maxReplicaCount` 3. The dependency
scales out and the queue falls to KEDA's target. Three replicas, not two, because two
replicas serve exactly the offered load and a queue at full utilisation does not drain.

The README carries three caveats. KEDA reads the metric through the Service, so each poll
sees one replica's queue, which is acceptable because the Service spreads the load evenly,
and the scaler's `aggregateFromKubeServiceEndpoints` with `aggregationType: sum` is the way
out when it is not. With the queue drained the dependency scales back down and up again,
and the HPA's scale-down stabilisation window only delays that. And a per-agent cap on
downstream calls is the backpressure that protects a dependency you cannot scale, it moves
the queue into the agent rather than removing it, and it is not what this lab shows.

`00-setup.sh` installs metrics-server, which `kind` does not ship, with
`--kubelet-insecure-tls`, and installs KEDA from its Helm chart at a pinned version.
Without metrics-server the HPA reports unknown and the broken state would be a lie.

CI asserts, in the first broken state, `dependency_queue_depth` above 40 and the HPA's
`desiredReplicas` at 1 with a numeric CPU reading present. In the second broken state,
the agent Deployment at 3 replicas, every replica taking tasks, and the queue higher than
it was when the third replica came up. The queue being above 40 proves nothing on its own,
because the backlog from the first observation keeps it there. In the fixed state, the
dependency at 2 or more replicas and the queue at or below 10.

### Disruption

Theory. A PodDisruptionBudget gates the eviction API only. A grace period cannot cover
a chain longer than itself. Checkpointing is what saves the work.

Lab. Break shows the eviction refusal, the delete succeeding, and the chain lost at two
grace values. Fix adds three things and repeats the delete and an OOM kill. A preStop
hook running `checkpoint.sh`, which calls `POST /checkpoint` on the agent, because a
script cannot read the process's memory. A SIGTERM handler in the agent that does the
same, as the fallback when no hook is set. And a periodic checkpoint after every step.
The README says preStop and SIGTERM are the same voluntary path, that SIGKILL skips
both, and that only the periodic checkpoint bounds the loss on involuntary paths. It
adds one line that the same kill drops the trace that would explain it, and points to
the observability lab, where the SDK lives, for the demonstration and the fix.

CI asserts the eviction API response code, the replacement pod's first log line, and
`lastState.terminated.reason` after the OOM.

To kill the agent without a graceful stop, set a memory limit and make the stub
allocate past it. Do not try
`kubectl exec -- kill -9 1`. A container cannot kill its own PID 1, because
`pid_namespaces(7)` only delivers SIGKILL to a namespace init from an ancestor
namespace, so the command reports success and nothing happens.

Karpenter cannot run on `kind`, so its manifests are reference only and live in
`labs/disruption/reference/` with a README line saying they are not run.

### Communication

Theory. Current MCP needs no session affinity when the server keeps no local state.
A2A Tasks are stateful and need a shared store to survive a replica change. Neither
protocol makes a retry safe by default, though A2A defines idempotency for some calls
and MCP defines none.

The client side has its own trap. A client that opens one connection to the MCP
Service and keeps it for the life of the process is pinned to one replica, because
kube-proxy balances per connection. New replicas never see its traffic, and a rollout
of the server pod kills the connection mid-task. A client that opens a connection per
request pays a handshake each call and has neither problem. Under the stateless
revision there is no session to lose, so the per-request client costs a round trip and
nothing else.

Lab. Two-replica stub Deployments behind one Service. Break shows the local-handle
failure and the A2A not-found. Fix shows the stateless server and the shared store.
The replay runs in both states. The client runs in both modes against the stateless
server, and the README carries the paragraph above.

The stubs speak A2A v1.0, so the methods are `SendMessage` and `GetTask`, the role is
`ROLE_USER` and the state is `TASK_STATE_WORKING`. MCP requests carry
`io.modelcontextprotocol/protocolVersion` in `_meta` and results carry `resultType`, which
the `2026-07-28` revision requires, because there is no handshake.

CI asserts four things. The stateless sequence returns a JSON-RPC result after hitting
two different replicas. The local-handle server returns a JSON-RPC error naming the
second replica. `GetTask` returns an error with local state and a result with the
shared store. The side effect log holds two lines without an idempotency key and one
line with one. A fifth check on the client. The persistent client's calls all name
the same replica, and the per-request client's calls name both.

### Observability

Theory. A trace crosses the agent boundary into an MCP tool call, because SEP-414 and
the OpenTelemetry MCP conventions define where the context travels. The A2A protocol
carries no trace context. The specification names tracing only as a design goal, the
Python SDK's client transports inject nothing, and two open proposals on the A2A
repository, #2103 and #2026, say the trace breaks at each delegation. Per-request HTTP
instrumentation on client and server does carry `traceparent` by header, because A2A is
JSON-RPC over one HTTP POST per message, and the stub uses none, which the README says.
That header stops helping once the message outlives the request, in streaming, in a task
resumed by a later request, and over gRPC, which is why both proposals put the context in
the message itself. Every span can be OK and
the answer wrong, and nothing in the GenAI conventions puts a quality signal on a span.
A `gen_ai.evaluation.result` event attached to the span after the fact carries one.
And a span is only exported once it ends. The batching processor holds finished spans
for up to five seconds by default, the Python SDK flushes them on `atexit`, and Python
skips `atexit` on a signal it does not handle. A pod killed mid-task loses its buffered
spans and never exports the span of the task it was running, because that span never
ended. On `kind` the delete also takes the whole grace period: Python is PID 1, and a
namespace init is not sent a signal it has no handler for, so nothing happens until the
SIGKILL at the end.

Lab. Stub agent, stub MCP server and stub A2A specialist with the OpenTelemetry SDK,
exporting to a file on a hostPath volume, so the file outlives the pod that wrote it.
On `kind` a hostPath lives inside the node container, so `labs/kind-config.yaml` carries an
`extraMounts` entry that maps it to a directory on the laptop, and the scripts and CI read
it from there. The path is relative, which means `kind create cluster` has to run from the
repository root.
The agent carries trace context in `params._meta` as the OpenTelemetry MCP conventions
define, and the server extracts it from there as the remote parent. HTTP headers alone
are not enough, because the conventions say header propagation covers the request and
not the individual MCP messages. The agent also delegates one step to the specialist
over A2A. Break has three parts. The green trace with the wrong answer. The specialist's
spans under a second trace id, because nothing carried the context across the JSON-RPC
hop. And a pod deleted mid-task whose trace never reaches the file. Fix runs the
evaluator, injects `traceparent` into the A2A message where #2103 and #2026 propose,
`message.metadata` under an extension URI, as well as the HTTP header, and extracts it
in the specialist. The README says this is our code following an open proposal, and
that the protocol has nothing normative here yet. Fix also adds a SIGTERM handler that
ends the open span with an event recording the interruption and calls `force_flush` before exit. The README says SIGKILL still loses
whatever the batch delay was holding, and that the termination grace period must leave
room for the flush.

CI asserts, in both states, one trace id across the agent span and the tool span, and
`gen_ai.operation.name` set to `invoke_agent` and `execute_tool` on them. In the
broken state it asserts the specialist span carries a different trace id and that the
deleted pod's trace id is absent from the file. In the fixed
state it asserts the specialist span carries the agent's trace id, the deleted pod's
agent span is present with the interruption event, the evaluation event's span id
matches the agent span, and every span except the interrupted one has status OK or unset.

## Build order

Probes, scaling, disruption, communication, observability. Probes first because it is
the reader's entry point. Scaling second because it is the largest build. Communication
next because it is the smallest. Observability last because it carries three
break states and depends on the A2A stub from communication.

## CI

GitHub Actions on `kind`. Every lab is small, so the private repository runner at
2 vCPU and 8GB fits all of them. No budget script is needed.

Both states are asserted. A workflow that only proves the fix says nothing about
whether the break still reproduces. Assertions read conditions, counts and API
responses, never wall clock seconds, because probe periods make timing a race.

Per pull request for the lab that changed, nightly for all five.

## Leak and slop gates

Hooks live in `hooks/`. Each clone runs `git config core.hooksPath hooks` once. This
step is in `CONTRIBUTING.md`. `hooks/checks.sh` holds the logic and is written in bash.
`hooks/pre-commit` and `hooks/pre-push` each call it, the first on staged content and
the second on the full tree.

It runs `gitleaks`, then rejects em dashes, smart quotes, unicode arrows, account IDs,
ARNs with digits and internal hostnames. When the repo goes public, GitHub push
protection is enabled as well. The hook exists from the first commit because a public
repository exposes its whole history.

## Collaboration

A first drop, the harness with the five labs, CI and the prose that describes them, lands
as one pull request of around 3700 lines. Split, it would ask for scripts to be reviewed
before the thing they run exists, and for a lab to be reviewed before the harness it stands
on. Read one lab end to end, then the other four as differences from it, because they are
the same shape on purpose.

A lab lands whole, as one pull request: stub, manifests, scripts, artifacts and the README
that explains them. None of those parts can be reviewed without the others. A lab runs 400
to 700 lines.

Everything else is one reviewable unit per pull request, 100 to 300 changed lines. Prose
that is not tied to one lab, the repository README and `CONTRIBUTING.md`, lands on its own.

The reviewer reads, so every lab PR body carries a pasted transcript of the break and the
fix and a link to the CI run.

## Open risks

All five labs run end to end on `kind` through their own scripts, on Kubernetes 1.37 with
rootless podman. Three things are unproven. The hooks have not run in full, because no
machine that runs the labs has `gitleaks` installed. CI has not run. And the agent's CPU in
the scaling lab reads between 25 and 55 percent of its request depending on the machine,
against a 70 percent target.
